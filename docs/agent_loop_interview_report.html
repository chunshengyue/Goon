Agent runtime / loop optimization

把循环变成
可恢复的系统。

这份报告解释 Goon 如何从“一次模型请求加固定工具链”演进为有界、可取消、可审计、可恢复的 Agent loop，并把设计取舍翻译成面试能讲清楚的工程语言。

核心判断Agent loop 不是 while 循环。它是一个由 Harness 控制的状态机：模型提出动作，运行时验证并执行，结果回灌，边界负责停止、恢复和升级。

当前代码落点

WebAgentRun.kt 负责项目工作流与模型/工具交替；AgentLoop.kt 提供预算、delivery queue、terminal reason 和 metrics 数据结构。

工具结果包含 toolCallId；结束时写入 agent_terminal，记录轮数、工具数、编辑数、模型/工具错误、重复调用和耗时。

为什么不直接引入 LangGraph

当前宿主是本地优先 Android App。引入 Python graph server 会增加部署、进程、网络和数据同步成本。项目只吸收 LangGraph 的 State/Checkpoint/Interrupt 思想，并用 Kotlin + SQLite/WebView 现有边界实现。

// interview answer: bounded harness loop
while (run.isActive) {
  state = checkpoint.load(threadId)
  messages = context.build(state)
  response = model.turn(messages, tools)
  if (response.isError) terminal(MODEL_ERROR)
  if (response.hasToolCalls) {
    validateBudgetAndPolicy(response.toolCalls)
    results = executeBatch(response.toolCalls)
    appendToolResults(results)
    checkpoint.save(state)
  } else {
    consumeSteerOrFollowUpOrStop()
  }
}

05 / Mock interview

模拟面试问答

点击展开
1. Agent loop 和普通 workflow 有什么区别？
答：普通 workflow 的路径通常由代码预先确定；Agent loop 允许模型在每一轮根据观察结果选择下一步工具。但它不能把控制权完全交给模型，运行时必须维护预算、权限、终止条件、checkpoint 和审计。我的项目里，模型只产生文本或 tool call，WebAgentRun 负责验证、执行、回灌和终止。
2. steer、follow-up、cancel 为什么要分开？
答：steer 是改变当前任务的下一步，必须等当前工具批次结束后注入；follow-up 是当前任务准备 idle 后才处理的后续工作；cancel 是立即中止当前模型/工具等待并保留未发布草稿。混成一个队列会让用户不知道消息何时生效，也会造成任务状态不可解释。
3. App 被杀死后怎么恢复？
答：每轮模型响应和每个工具结果后写 checkpoint，保存项目草稿、manifest、最近消息、两类消息队列、编辑/验证状态、预算计数和 graph snapshot。恢复时先校验 baseRevision，防止旧草稿覆盖新版本，再恢复消息上下文继续请求模型。原始事件仍保存在 trace 中，checkpoint 是执行游标，不是唯一历史。
4. 工具超时后为什么不能直接重试？
答：超时只说明调用方没有拿到结果，不代表外部副作用没有发生。文件写入、订单、发消息等操作要用 toolCallId + idempotencyKey，状态经历 PREPARED、SUCCEEDED、FAILED 或 UNKNOWN；UNKNOWN 先查询再决定是否重试。当前 Web 项目写入采用私有草稿和 revision 校验，避免重复发布；未来有外部副作用时需要显式确认协议。
5. 如何防止 Agent 无限循环？
答：至少有四层：最大轮数、总工具预算、时间预算、重复 tool name + arguments 检测。当前实现是 24 轮、单轮 16 工具、总计 128 工具、15 分钟、连续 3 次相同调用熔断，并写 LOOP_DETECTED 或 BUDGET_EXCEEDED terminal reason。工具错误会回灌模型一次，但不会盲目无限重试。
6. 工具调用什么时候并行，什么时候串行？
答：读文件、独立搜索这类无副作用调用可以并行；写文件、patch、运行和验证有依赖，必须串行并保持结果顺序。当前版本选择串行，优先保证移动端文件工作流的确定性；下一步可为工具声明 read-only、commutative、exclusive 能力，再安全并行。
7. 长任务上下文超过模型窗口怎么办？
答：原始轨迹和结构化工件持久化在本地，模型上下文只保留系统约束、目标、当前计划、最近工具结果和未完成队列；大型文件/搜索结果只在需要时重新读取。压缩前写 checkpoint，保留引用和摘要，不能把失败证据直接丢掉。当前代码先用最近 80 条消息和每条 20,000 字符硬上限，语义压缩属于下一步。
8. 为什么不能相信模型说“已完成”？
答：完成必须由 evaluator 证明。当前 Web Agent 要求最后一次文件修改后运行隔离 WebView，执行 click/type/assertText/assertCount/assertVisible，并检查 JS、资源和溢出；只有 verified revision 才允许 finish。模型文本只是叙述，不是证据。
9. 你会如何评估 loop 质量？
答：任务成功率只是结果指标，还要看平均/P95 轮数、工具失败率、参数拦截率、重复调用熔断次数、恢复成功率、steer 生效延迟、首 token/总耗时、token/费用和 terminal reason 分布。优化目标是成功率上升，同时无效调用和恢复成本下降。
10. 为什么不直接用 LangGraph 或 MCP SDK？
答：LangGraph 的价值在 State、Node、Edge、checkpoint 和 interrupt 语义；MCP 的价值在标准化 tools/resources/prompts 与 transport。当前产品是 Kotlin Android、本地优先、受限 WebView，直接引入 Python 服务或任意外部进程会增加部署和安全边界。我先实现必要协议和可观测性，等 transport、权限和连接生命周期确定后再引入 SDK。
